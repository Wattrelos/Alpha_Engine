# Adaptação da Arquitetura para Java, Thymeleaf e Padrão Hydrator

**Implementação**
- Criação do arquivo de representação visual `diagrama_de_arquitetura.mmd` utilizando sintaxe Mermaid.
- Estruturação das camadas respeitando o fluxo limpo (Clean Architecture) portado para componentes do ecossistema Java (Spring MVC, JDBC, Records).
- Inserção do padrão `Hydrator` como intermediário entre a obtenção de dados brutos (DAO/ResultSet) e as camadas de Domínio (Entidades/DTOs).

**Motivo**
- Atender à demanda de projeção arquitetural em uma pilha de tecnologia diferente (Java + Thymeleaf), demonstrando como os padrões agnósticos de framework (Repository, DTO e Presenter) se comportam e se integram com o Padrão Hydrator para manter o ecossistema robusto.

**Benefício**
- A inclusão do **Hydrator** assegura o encapsulamento das Entidades em Java (evitando a exposição indesejada via *setters* públicos). O uso de DTOs nativos (como *Java Records*) e Thymeleaf resulta em um tráfego de dados previsível, type-safe e performático até a renderização visual final.

## Resposta Completa do Assistente
Para adaptar a arquitetura limpa do projeto para o ecossistema **Java** (com **Thymeleaf** no frontend) e introduzir o padrão **Hydrator**, manteríamos a responsabilidade estrita das camadas, aproveitando os recursos da linguagem, como tipagem forte, `Records` (para DTOs) e a API de *Reflection*.

### O Papel do Hydrator
O **Hydrator** atua como uma ponte especializada entre os dados brutos e o domínio. Em Java, ele evita a criação de métodos `setters` anêmicos nas Entidades. Ao ler um `ResultSet` (via JDBC, por exemplo), o Hydrator usa *Reflection* (ou construtores fechados) para popular o estado interno das Entidades de Domínio ou gerar instâncias imutáveis de DTOs, garantindo 100% de encapsulamento.

### Como funciona o fluxo (Java + Thymeleaf):
1. **Banco -> DAO**: A camada de persistência extrai um `ResultSet` ou mapa estruturado.
2. **DAO -> Hydrator**: O Hydrator injeta esses dados nas propriedades da classe, retornando Entidades (para regras de negócio) ou Records/DTOs (somente leitura).
3. **Repository**: Coordena o acesso chamando o Hydrator e retorna os objetos ricos para a aplicação.
4. **Presenter -> Controller**: O Controller (ex: Spring MVC) invoca o Presenter para preparar valores formatados (moedas, datas) e adiciona o DTO higienizado no `Model` (ex: `model.addAttribute("store", storeViewDto)`).
5. **Thymeleaf**: Renderiza a resposta consumindo o modelo de forma segura via tags nativas (ex: `th:text="${store.name}"`).
