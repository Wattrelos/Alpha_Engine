# Expansão Arquitetural: Inclusão do Fluxo de Escrita e Request Hydrator

**Implementação**
- Inserção dos nós `ReqHydrator` (Request Hydrator / Data Binder) e `InputDTO` no arquivo `diagrama_de_arquitetura.mmd`.
- Adição do mapeamento visual do fluxo de escrita (Request Flow), ilustrando o envio de dados via formulário HTML (POST) partindo do Thymeleaf, sendo interceptado pelo Hydrator de requisição e convertido em um objeto seguro (Input DTO) que é enviado ao Repositório.

**Motivo**
- Atender ao questionamento sobre a utilidade do padrão Hydrator na conversão de dados de formulários HTTP. Diferenciar conceitualmente o "Database Hydrator" (que mapeia colunas do banco para Entidades/Read DTOs) do "Request Hydrator" (que mapeia `$_POST` ou payloads JSON para Input DTOs/Commands).

**Benefício**
- O diagrama de arquitetura agora reflete o ciclo de vida completo de uma aplicação web transacional: O **Fluxo de Leitura** (subindo do DB até a View via Read Models protegidos por Cache) e o **Fluxo de Escrita** (descendo da View até o DB via Input DTOs higienizados por um Data Binder/Hydrator). Isso consolida os pilares da Arquitetura Limpa (Clean Architecture), onde os dados em trânsito são sempre objetos definidos (DTOs) ao invés de arrays amorfos.

## Questão
Dúvida de leigo: O hydrator também pode ser usado para preencher objetos com dados dos formulários html? Como ficaria no diagrama?

## Resposta Completa do Assistente
Essa não é uma dúvida de leigo, pelo contrário, é uma observação arquitetural excelente! 

Sim, o padrão **Hydrator** (frequentemente chamado de *Data Binder*, *Request Hydrator* ou *Form Mapper*) é amplamente utilizado para capturar dados brutos vindos de requisições HTTP (como um `POST` de um formulário HTML) e preencher **Input DTOs** ou **Commands**. 

Em frameworks como o Spring Boot (Java), isso muitas vezes acontece de forma mágica nos bastidores por meio da anotação `@ModelAttribute` ou `@RequestBody`, onde o framework hidrata automaticamente um DTO com os dados do formulário para você.

No diagrama de arquitetura, esse fluxo representa o **caminho de escrita** (Request Flow), correndo na direção oposta ao caminho de leitura que já desenhamos. 

Fiz a atualização do diagrama para incluir um `Request Hydrator` e um `Input DTO` demonstrando como o `Thymeleaf` enviaria um formulário para o `Controller`, que o hidrataria antes de enviar ao `Repository` (ou a um Service) para salvar no banco.
