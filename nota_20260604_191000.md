# Otimização: Eliminação de N+1 Queries no ProductMapper

**Implementação**
Refatoração do método `ProductMapper::getAttributes` para substituir múltiplas queries em loop (N+1) por uma única query que busca todos os dados de atributos e os agrupa em PHP. A complexidade de acesso ao banco de dados foi reduzida de O(N) para O(1).

**Motivo**
A implementação original do método `getAttributes` causava um gargalo de desempenho severo em páginas de produto com muitas especificações técnicas. Para cada grupo de atributos, uma nova consulta era disparada, resultando em dezenas de queries desnecessárias e aumentando o tempo de carga da página.

**Benefício**
Redução drástica do número de queries ao banco de dados, resultando em um carregamento significativamente mais rápido das páginas de produto. A otimização melhora o TTFB (Time To First Byte), a experiência do usuário e diminui a carga sobre o servidor de banco de dados, além de preparar o terreno para um cache mais eficiente na camada de Repositório.

## Questão
Maravilha! A loja está funcionando perfeitamente. Deseja auditar os Mappers associados (como **ProductMapper.php** ) para garantir que eles também estejam delegando o cache das queries diretas para o CacheStrategy?

## Resposta Completa do Assistente
Com certeza! Auditar os Mappers é o próximo passo lógico para garantir que o novo `CacheStrategy` seja aproveitado ao máximo, eliminando gargalos de I/O no banco de dados.

Uma observação importante sobre a nossa arquitetura: a responsabilidade de orquestrar o cache (verificar se um dado existe, buscá-lo no banco se não existir e armazená-lo) pertence à camada de **Repositório** (`Repository`). A camada de **Mapper** (`Mapper`) deve se concentrar exclusivamente em sua tarefa: mapear os dados do banco para objetos/arrays, sem conhecer a lógica de cache.

O `CategoryRepository` que otimizamos anteriormente segue exatamente esse padrão.

Dito isso, ao auditar o `ProductMapper.php`, encontrei uma oportunidade de otimização ainda mais fundamental e crítica que o próprio cache: a **eliminação de um problema de N+1 Queries** no método `getAttributes`.

Este método, responsável por buscar as especificações técnicas de um produto, primeiro busca os grupos de atributos e depois, dentro de um loop, executa uma nova query para cada grupo. Para um produto com 10 grupos de atributos, isso resulta em 11 queries ao banco.

A correção que estou aplicando abaixo refatora o método para usar uma **única query**, que busca todos os dados de uma vez e os organiza em PHP. Isso reduz o número de queries de `N+1` para apenas `1`, um ganho de performance massivo, especialmente em páginas de produto.
