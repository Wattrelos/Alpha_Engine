# Refatoração: Extensão do Cache-Aside para Métodos Base de Produtos

**Implementação**
Adição da estratégia de *Cache-Aside* diretamente nos métodos base `getProducts` e `getTotalProducts` dentro de `ProductRepository`. Utilizou-se geração de hash MD5 consistente (com `ksort`) sobre os parâmetros de filtragem combinados com os IDs de idioma, loja e (quando aplicável) grupo de clientes. O TTL foi mantido em 5 minutos.

**Motivo**
Embora o método de orquestração `getSearchData` já contasse com cache, chamadas diretas de outros serviços ou módulos do sistema para `getProducts` e `getTotalProducts` acabavam vazando para o banco de dados. Como o design arquitetural estipula que a camada de `Mapper` não deve conter regras de orquestração de memória (Cache), tornou-se mandatório proteger esses métodos na camada de `Repository`.

**Benefício**
Isolamento completo e definitivo do banco de dados para listagens de produtos iguais. Qualquer componente, seja uma API de terceiros, módulo de vitrine ou página de categoria que chame esses métodos receberá os dados cacheados na memória (O(1)), respeitando a reponsabilidade exclusiva (SRP) de cada camada do software.

## Questão
Essa otimização atende às listagens, mas as chamadas diretas como o getProducts() e getTotalProducts() dentro do Mapper também possuem cache?

## Resposta Completa do Assistente
Excelente observação arquitetural! 

Para responder de forma direta: **Não, os Mappers não possuem cache, e isso é proposital pelo nosso design de software.** Na nossa arquitetura, a camada de **Mapper** tem a responsabilidade exclusiva de conectar-se ao banco de dados e mapear os resultados (Data Mapper Pattern). A responsabilidade de verificar se um dado existe na memória, orquestrar o tempo de vida (TTL) e gravar o cache pertence inteiramente à camada de **Repositório** (Repository Pattern).

No entanto, você tocou no ponto perfeito: se alguma outra parte do sistema (como um módulo de vitrine ou API) chamar os métodos públicos `getProducts()` ou `getTotalProducts()` diretamente no `ProductRepository` ignorando o `getSearchData()`, **essas chamadas passariam direto para o banco de dados**, pois os métodos base no Repositório ainda não possuíam sua própria estratégia de cache.

Para fechar essa lacuna de segurança de desempenho, estou implementando o padrão *Cache-Aside* diretamente nesses dois métodos base dentro do `ProductRepository`. Dessa forma, não importa por onde a aplicação chame a lista de produtos, ela sempre estará protegida.
