# Refatoração Semântica do EntityMapper para EntityHydrator

**Implementação**:
- Criação da classe `EntityHydrator` no diretório/namespace `Alpha\Support`, mantendo os métodos de reflexão, sanitização e validação.
- Remoção do arquivo obsoleto `core/Model/DataTransferObject/EntityMapper.php`.
- Atualização das importações e referências estáticas nos repositórios `CustomerRepository`, `CustomerAffiliateRepository` e `AddressRepository`.
- Execução de `composer dump-autoload` para atualizar o mapa de classes otimizado do Composer.

**Motivo**:
- A classe original `EntityMapper` não é um DTO (Data Transfer Object), portanto não deve habitar o diretório `core/Model/DataTransferObject/`.
- O nome "Mapper" colide conceitualmente com os Data Mappers de banco de dados do projeto (ex: `ProductMapper`, `CustomerMapper`), que executam queries SQL e persistem dados no banco.
- O padrão que realiza a cópia e conversão reflexiva de arrays (especialmente dados de requests) para propriedades de objetos de domínio é semanticamente conhecido como **Hydrator** (ou *Object Hydrator*).

**Benefício**:
- **Clareza Arquitetural**: Elimina a confusão entre o que é persistência de banco de dados (Mappers) e o que é manipulação de objetos/requests em memória (Hydrators).
- **Consistência de Padrões**: Alinha o projeto a padrões de design OOP bem definidos (Data Mapper vs Hydrator).
- **Limpeza de Diretórios**: Remove arquivos utilitários de pastas exclusivas para estruturas de dados (DTOs).

## Questão
@[/var/www/html/agsonhos/core/Model/DataTransferObject/EntityMapper.php] Eu acho que cometi um erro de semântica, pois este arquivo está em uma pasta DTO e o nome é Mapper, porém, aparentemete, implementa o padrão Hydrator. Devo renomeá-lo e movê-lo para uma pasta com a semântica adequada?

## Resposta Completa do Assistente
Sim, você está absolutamente correto em sua análise semântica. 

No design de arquitetura de software moderno e DDD (Domain-Driven Design):
1. **DTOs (Data Transfer Objects)** são objetos de transporte simples, que contêm apenas dados (propriedades) e opcionalmente getters/setters simples, sem qualquer lógica de processamento ou comportamento reflexivo. A classe `EntityMapper` realiza reflexão, sanitização contra XSS e validação, portanto não é um DTO.
2. **Data Mappers** (como `ProductMapper` e `CustomerMapper` sob `core/Mappers/`) são responsáveis pela persistência física e comunicação SQL direta com o banco de dados. Ter uma classe utilitária de reflexão em memória chamada `EntityMapper` cria ambiguidade e confunde o desenvolvedor.
3. O padrão que preenche propriedades de um objeto de domínio a partir de uma fonte de dados estruturada em array (e vice-versa) é formalmente denominado **Hydrator** (padrão Hydration).

Dessa forma, a melhor decisão arquitetural e semântica é:
- Renomear a classe para **`EntityHydrator`**.
- Movê-la para o namespace e diretório de utilidades globais do core: **`Alpha\Support\EntityHydrator`** (salvando o arquivo em `core/Support/EntityHydrator.php`).
- Remover o arquivo antigo `core/Model/DataTransferObject/EntityMapper.php`.
- Atualizar todas as importações e chamadas estáticas nos repositórios que a utilizam (`CustomerRepository`, `CustomerAffiliateRepository`, `AddressRepository`).
- Executar `composer dump-autoload` para atualizar as referências mapeadas de forma estática pelo Composer.

Criei um plano de implementação para realizar essa refatoração de forma segura e consistente. Aguardo sua aprovação para prosseguirmos com a alteração.
