# Refatoração: Desacoplamento e Encapsulamento do customField (Customer)

**Implementação**: A assinatura do método `setCustomField` na entidade `Customer` foi alterada para aceitar `string|array` (Union Type). Caso um array seja recebido, a própria entidade se encarrega de serializá-lo com `json_encode()`. Também foi criado o método auxiliar `getCustomFieldArray()` para devolver o JSON decodificado.

**Motivo**: A coluna no banco de dados é do tipo `text` e comumente armazena JSONs. Remover a coluna da entidade faria a Alpha Engine perder a funcionalidade vital de Campos Personalizados do OpenCart. Modificar a propriedade interna da Entidade para `array` faria com que o DataAccessObject (DAO) pulasse a gravação no banco, pois ele contém uma regra para ignorar propriedades não-escalares (`if ($paramType === 'array') continue;`).

**Benefício**: Preserva o princípio de **encapsulamento** da Programação Orientada a Objetos. O resto do sistema não precisa saber como os dados são serializados no banco. Mappers e controllers podem passar Arrays nativos do PHP diretamente ao Set, e a entidade os formatará. Simultaneamente, o DAO continuará lendo o contrato da propriedade primária (`private string $customField`) como string, conseguindo hidratar a Entidade durante a consulta no banco de dados e gravar a string no insert sem conflitos.

## Resposta Completa do Assistente
Não, **não devemos excluir esse campo**. Os *Custom Fields* (Campos Personalizados) são uma das funcionalidades mais flexíveis do ecossistema OpenCart (usados para capturar CPF, RG, Data de Nascimento, etc., dependendo das configurações da loja). Se removermos o campo, quebraremos formulários de registro, checkout e a compatibilidade com o painel administrativo.

Como você bem pontuou, a grande vantagem da Programação Orientada a Objetos (POO) é o **encapsulamento e o desacoplamento**. Nós não precisamos que a nossa aplicação inteira saiba que o banco de dados armazena um texto em JSON, e também não precisamos alterar o *DataAccessObject* (DAO) só por causa desse campo.

Podemos lidar com isso de forma extremamente elegante na própria Entidade `Customer`, transformando-a em uma "caixa preta" que entende os dois mundos: se mandarem um Array (do formulário), ela converte para String (JSON) internamente; se o DAO mandar uma String (do banco de dados), ela aceita normalmente. E para as regras de negócio lerem isso facilmente, criamos um método auxiliar `getCustomFieldArray()`.

(As alterações de tipagem e a lógica do setter/getter inteligente foram aplicadas ao arquivo `/var/www/html/agsonhos/core/Model/Domain/Entities/Customer.php` preservando a compatibilidade total com a hidratação de Reflexão do DAO).
