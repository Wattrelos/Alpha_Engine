# Refatoração: Event Delegation para Interação de Wishlist

**Implementação**: Adição de um event listener global em `app.js` preparado para escutar os cliques nos novos seletores blindados de ação de lista de desejos (`.egen-add-to-wishlist-btn`). Utilizou-se o método de Delegação de Eventos (`event.target.closest`).

**Motivo**: Como a marcação no DOM dos cartões de produtos (`product-card.html.twig`) foi atualizada removendo classes legadas do sistema antigo em favor do *Scoped CSS* (`egen-`), o script de Client-Side precisava ser atualizado ou integrado para garantir que os gatilhos capturassem perfeitamente a iteração do usuário (Evitando botões "órfãos").

**Benefício**: O uso de Event Delegation previne vazamentos de memória (memory leaks) e permite que a ação funcione organicamente em cartões que venham a ser injetados no DOM dinamicamente (via paginação em AJAX, fetchs ou infinite scroll) sem a necessidade de reatar (re-bind) o listener múltiplas vezes.

## Resposta Completa do Assistente
Com certeza! Você tocou em um ponto fundamental: sempre que refatoramos as marcações no HTML (DOM) para usar novos identificadores ou classes isoladas (como foi o caso do `.egen-add-to-wishlist-btn`), precisamos garantir que o JavaScript acompanhe essa mudança, do contrário, a ação ficará "órfã" e o clique do usuário não terá efeito.

Ao analisar o seu arquivo `app.js`, notei que ele atualmente cuida muito bem das interações visuais (como o Header Sticky e os menus responsivos), mas **ainda não possuía** o "listener" (escutador) para capturar o clique na lista de desejos. O script antigo que usava a classe `.add-to-wishlist-btn` devia estar perdido em algum `common.js` antigo do código legado.

A melhor abordagem arquitetural agora é centralizarmos essa interação no `app.js` usando **Event Delegation** (Delegação de Eventos). Isso garante que o botão funcionará mesmo se os cartões de produto forem carregados dinamicamente via AJAX no futuro (como em uma rolagem infinita ou filtros de categoria).
