# Otimização: Cache-Aside de Granularidade Fina no ProductRepository

**Implementação**
Refatoração do `ProductRepository` adicionando métodos granulares (`getProductImages`, `getProductAttributes`, `getProductDiscounts`, `getProductCodes`, `getRelatedProducts`) equipados com o padrão **Cache-Aside**. O método orquestrador `getProductDisplayData` foi atualizado para consumir esses métodos nativos cacheados em vez de acionar o `ProductMapper` diretamente no banco de dados.

**Motivo**
A página de produto na Alpha Engine demanda múltiplos blocos de dados pesados e estáticos (como descrições de abas de especificações, imagens secundárias e opções de variantes). Anteriormente, a chamada para `getProductDisplayData` delegava a montagem a diversas queries sequenciais. Embora o mapper de atributos já tivesse o N+1 sanado, realizar acessos ociosos ao banco para dados idênticos em alto tráfego representa um gargalo escalável de infraestrutura.

**Benefício**
Blindagem absoluta contra picos de tráfego (Slashdot effect). Com chaves de contexto precisas combinando `$productId`, `$language_id`, `$store_id` e até `$customerGroupId` (para descontos b2b/varejo), a construção do Grafo de Exibição do Produto foi transmutada em memória O(1). Além disso, essa granularidade protege outros serviços periféricos (como o Carrinho de Compras) que frequentemente validam opções de produtos, garantindo performance extrema no checkout.

## Resposta Completa do Assistente
Com toda certeza! Como você muito bem pontuou, a responsabilidade de orquestrar a memória e poupar o banco de dados pertence exclusivamente à camada de **Repositório** (`Repository`). 

Observando a nossa estrutura, o arquivo `ProductRepository.php` já existe no nosso ecossistema e já possui um escopo excelente. O que faremos agora é injetar o poder do **Cache-Aside Pattern** que discutimos em todas as engrenagens que compõem a Página do Produto (Imagens, Atributos, Opções, Descontos, Assinaturas e Produtos Relacionados).

Com a refatoração abaixo, o método orquestrador `getProductDisplayData()` passará a consumir métodos de granularidade fina do repositório em vez de invocar o `ProductMapper` diretamente. Isso significa que, após a primeira visita, as subsequentes não baterão no banco de dados para construir a página, respondendo em microssegundos (O(1) Memory Hit)!
