# Refatoração do AuthService com Injeção de Dependência e Delegação de Autenticação

**Implementação**
1. **Remoção de Acoplamento Direto com a Camada de Dados**: Removemos a instanciação e o uso direto do `DataAccessObject` e da entidade `Customer` de dentro do `AuthService`.
2. **Injeção de Dependência**: Adicionamos o `CustomerRepository` como dependência injetada no construtor da classe `AuthService`, com um fallback seguro utilizando a `RepositoryFactory::getInstance()` para retrocompatibilidade caso não seja injetado via container.
3. **Delegação da Autenticação**: O método `authenticate` foi simplificado e agora delega a validação segura da credencial para a função `$this->customerRepository->authenticate($email, $password)`, que já lida corretamente com algoritmos de hash seguros (`password_verify`) e re-hashing progressivo (`password_needs_rehash`).
4. **Habilitação de Tipagem Estrita e Correções de Sintaxe**: Adicionamos `declare(strict_types=1);` no topo do arquivo, tipamos estritamente todas as propriedades da classe (`RedisClient $redis` e `?CustomerRepository $customerRepository`), removemos a declaração inválida de tipo de variável local (`DataAccessObject $dataAccessObject`), e corrigimos a falta do caractere de final de instrução `;` que gerava o erro de Parse do PHP.
5. **Correção do Namespace de Importação**: O `use Alpha\Model\Repositories\CustomerRepository;` incorreto foi substituído por `use Alpha\Model\Domain\Repositories\CustomerRepository;`.

**Motivo**
* O código anterior continha erros de sintaxe críticos que impediam a execução básica da classe.
* Realizar queries de banco de dados e instanciar entidades diretamente no `AuthService` quebra a topologia de camadas (separação de responsabilidade) da Alpha Engine, na qual serviços de aplicação devem depender de abstrações de repositório, não de mappers ou DAO diretamente.
* Comparar senhas em texto plano usando operadores simples (`===` ou `==`) é uma falha gravíssima de segurança. O repositório já centraliza essa lógica de domínio com verificação robusta de hash (`password_verify`).

**Benefício**
* **Segurança Reforçada**: Agora o sistema valida hashes de senhas modernos (Bcrypt/Argon2) de forma transparente, permitindo atualizações progressivas de segurança sem impactos no controller ou na camada de serviço.
* **Separabilidade de Responsabilidades e Testabilidade**: O `AuthService` passa a ser testável unitariamente (mockando o `CustomerRepository` e o `RedisClient`), sem acoplamento rígido ao banco de dados relacional.
* **Conformidade com a Alpha Engine**: O código adota os padrões modernos de design e arquitetura estabelecidos no projeto, eliminando débitos de sintaxe antigos.

## Questão
@[/var/www/html/agsonhos/core/Services/Auth/AuthService.php] O que seria boa prática, implementar a função authenticate para buscar o objeto Customer via CustomerRepositoy? Como deixar o código mais profissional?

## Resposta Completa do Assistente
Sim, é uma excelente boa prática. Na verdade, na arquitetura da **Alpha Engine**, essa é a abordagem recomendada e padrão de design para respeitar a topologia de camadas (Domain-Driven Design com Repository Pattern). 

### O que torna o código mais profissional:

1. **Separação de Responsabilidades (SRP)**:
   O `AuthService` (serviço de aplicação) não deve interagir diretamente com o banco de dados via `DataAccessObject` nem se preocupar com como os dados de clientes são persistidos. Ele deve depender do `CustomerRepository` (camada de domínio) para obter e autenticar o cliente.
   
2. **Segurança Avançada e Criptografia**:
   A autenticação de senhas nunca deve comparar strings brutas (como `$password == $customer->getPassword()`). O `CustomerRepository` encapsula o uso de `password_verify()` com suporte a `password_needs_rehash()`, atualizando senhas legadas automaticamente na primeira autenticação bem-sucedida.

3. **Injeção de Dependências**:
   Ao invés de usar `new` para instanciar classes de infraestrutura dentro de métodos, injetamos as dependências (`CustomerRepository` e `RedisClient`) via construtor. Isso permite testar a classe substituindo o banco real por mocks/stubs.

4. **Tipagem Estrita e Limpeza de Sintaxe**:
   * Adição de `declare(strict_types=1);` para assegurar a tipagem forte do PHP 8.4.
   * Tipagem de propriedades nativas de classe (`private RedisClient $redis;`).
   * Correção dos erros graves de sintaxe (como a falta de `;` na linha 39 e a tipagem local inválida de variáveis como `DataAccessObject $dataAccessObject`).
   * Correção da importação incorreta do repositório (`use Alpha\Model\Domain\Repositories\CustomerRepository;`).

O arquivo `core/Services/Auth/AuthService.php` foi inteiramente refatorado seguindo essas diretrizes.
