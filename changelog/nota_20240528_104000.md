# Refatoração: Modernização do Fluxo Final de Pagamentos no Checkout

**Implementação**
- Criação do controlador de ação assíncrono `ProcessPaymentAction.php` sob o namespace da Alpha Engine (`Alpha\Controller\Actions\Checkout`).
- Integração estrita da interface `UnitOfWorkInterface` para envolver a busca do pedido, a futura chamada de gateway de pagamento, a mudança de status e a limpeza do carrinho dentro de uma única transação atômica (`begin`, `commit`, `rollback`).
- Implementação de validações robustas com tratamento de exceções devolvidas como JSON de erro HTTP 400 em caso de falha.

**Motivo**
- O fluxo de pagamentos antigo fragmentava a responsabilidade da alteração do status do pedido e da chamada ao gateway, criando gargalos de banco de dados e riscos altos de dessincronização (onde o usuário paga, mas o banco falha na atualização, mantendo o pedido no status `0`).
- O processo de fechamento exigia um controlador especializado focado inteiramente na orquestração segura (Skinny Controller).

**Benefício**
- Prevenção absoluta contra corrupção de dados: se a operadora do cartão recusar ou o servidor falhar ao limpar o carrinho, o banco sofre `rollback` e o status do pedido não avança incorretamente.
- O novo código possui acoplamento baixo, permitindo a injeção limpa de uma futura `PaymentGatewayFactory` para gerenciar múltiplos métodos (Pix, Cartão, Boleto) transparentemente.

Podemos focar no controlador do Checkout. Vamos modernizar o fluxo final de pagamentos.

## Resposta Completa do Assistente
Excelente escolha! O fluxo final de pagamentos é uma das áreas mais críticas do e-commerce. Na arquitetura antiga (OpenCart), os pagamentos eram processados em controladores extensos que misturavam a comunicação com a API do gateway (Stripe, Mercado Pago, Pix, etc.), a atualização do banco de dados e a limpeza da sessão, o que frequentemente causava perda de dados ou pedidos travados com status `0` se a conexão oscilasse.

Para modernizar isso na **Alpha Engine**, vamos criar uma Action dedicada (`ProcessPaymentAction`) que orquestra esse fechamento utilizando o **Unit of Work (UoW)**. Isso garante a atomicidade: ou o pedido é marcado como pago, o gateway confirma e o carrinho é limpo, ou tudo sofre *Rollback* automaticamente, mantendo a integridade do banco.
