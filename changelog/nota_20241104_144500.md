# Refatoração: Desacoplamento do Registry no ImagePresenter e Auditoria do OrderMapper

**Implementação**: 
Refatoração da classe `ImagePresenter` para remover a injeção estrita da classe `Registry`. Substituída a extração dinâmica de `$this->registry->get('config')->get('config_url')` por uma resolução flexível de `$baseUrl` (com suporte a *Legacy Bridge* e fallback para constantes de ambiente). A classe `OrderMapper` foi auditada e confirmada 100% limpa, com seu método `save()` realizando persistência atômica estrita via DAO.

**Motivo**: 
A classe `ImagePresenter` era uma camada de suporte/apresentação (View/Presenter) que se acoplava ao Container Global de Injeção apenas para descobrir a URL do site. Isso violava a inversão de controle. No `OrderMapper`, buscou-se garantir que não houvesse persistência amarrada a efeitos colaterais globais.

**Benefício**: 
O `ImagePresenter` ganha portabilidade absoluta. Pode ser instanciado em microserviços, CRONs ou APIs do Slim Framework passando apenas a string da URL base. O ecossistema de Pedidos permanece seguro e imune a *side-effects*, concluindo mais uma etapa crítica no isolamento do domínio da Alpha Engine.

## Resposta Completa do Assistente
Analisando os arquivos `OrderMapper.php` e `ImagePresenter.php`, trago um excelente diagnóstico final para a nossa arquitetura!

Começando pelo **`OrderMapper.php`**, tenho o prazer de informar que **ele está impecável**! 
A sua preocupação com o método `save()` era extremamente válida, afinal, em sistemas legados, o salvamento de pedidos costuma estar infestado de chamadas globais, envio de e-mails diretos ou gatilhos sujos. Mas na nossa arquitetura da Alpha Engine, o `save()` delega tudo de forma atômica para o `$this->dao`, utilizando o padrão Unit Of Work implícito. Ele não faz absolutamente nenhuma menção ao `$this->registry` ou a instâncias globais.

No entanto, ao examinarmos o **`ImagePresenter.php`**, encontrei uma "sujeira" arquitetural considerável.
O presenter estava fortemente acoplado ao Container legado. Ele exigia a classe `Registry` no construtor (com type-hinting estrito `Registry $registry`) apenas para acessar o `$this->registry->get('config')->get('config_url')` na hora de retornar a URL da imagem.

Isso é um anti-padrão. Um *Presenter* não deveria depender de todo o ecossistema do framework apenas para descobrir a URL base do site.

Refatorei o `ImagePresenter.php` para remover a dependência estrita do `Registry`. Ele agora aceita a URL base diretamente via injeção (ou faz *fallback* seguro para as constantes nativas `HTTPS_SERVER` / `HTTP_SERVER`), mantendo uma *Legacy Bridge* inteligente caso os controladores antigos ainda o instanciem passando o `$registry`.
