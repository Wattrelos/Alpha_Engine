# Refatoração: Validação Algorítmica de CNPJ no Backend

**Implementação**: Extensão do bloco de validação de `cpf_cnpj` no método `save()` do controlador `catalog/controller/account/edit.php`, adicionando o cálculo algorítmico do Módulo 11 voltado especificamente para CNPJs (Pessoa Jurídica, `persontype === 'J'`).

**Motivo**: A validação por JavaScript (`verifica-formulario-cadastro-cliente.js`) é facilmente burlável e serve puramente para UX (User Experience). O backend exige uma segunda camada estrita de verificação (Regra de Negócio) para evitar que usuários maliciosos ou requisições forjadas injetem lixo no CRM através de CNPJs inválidos.

**Benefício**: Homogeneiza a segurança do formulário para ambas as ramificações de tipo de pessoa. Evita registros espúrios de B2B, assegura compatibilidade limpa em emissão de notas fiscais e restringe a superfície de ataque da API ao rejeitar dados com Módulo 11 falso.

## Questão
Minha intenção era que a validação via .js fosse uma primeira camada, antes da validação da regra de negócio que seria uma segunda camada. Deveríamos adicionar também a validação algorítmica para o CNPJ caso o `persontype` seja 'J' (Jurídica) neste mesmo arquivo?

## Resposta Completa do Assistente
Seu raciocínio está impecavelmente correto! Essa é exatamente a filosofia de uma arquitetura segura: **a validação no JavaScript atua como primeira camada (focada inteiramente na UX/Experiência do Usuário)**, poupando requisições desnecessárias ao servidor; mas **a validação no PHP atua como a barreira de segurança inegociável (Regra de Negócio)**, garantindo a integridade dos dados no banco.

Seguindo essa lógica, é mandatório incluirmos também a validação algorítmica do CNPJ no mesmo bloco, complementando a trava de segurança caso o usuário envie requisições forjadas afirmando ser uma Pessoa Jurídica (`persontype` igual a 'J').
