# Refatoração: Remoção de Acoplamento Estático no Flow de Checkout

**Implementação**: Substituição das chamadas estáticas `\Alpha\Model\DataAccessObject\ConnectionDB::getRegistry()` pelo uso nativo de injeção de dependência via `$this->registry` nas classes `TotalMapper`, `PaymentMapper` e `ShippingMapper`.

**Motivo**: Esses mappers precisavam do Registry do OpenCart para carregar dinamicamente extensões legadas (`total`, `payment`, `shipping`). Contudo, eles já estendiam o `BaseMapper`, que possui o Registry injetado no construtor. Ao invocar estaticamente a classe abstrata de driver do banco (`ConnectionDB`) para obter o Registry, estávamos quebrando o isolamento de camadas, violando a Inversão de Dependência e criando um acoplamento desnecessário com o banco de dados dentro de uma lógica de carregamento de módulo.

**Benefício**: Restaura o princípio de *Dependency Injection*. O código passa a ser mais limpo, fácil de simular em testes unitários e respeita integralmente a arquitetura da Alpha Engine (onde Mappers usam o ambiente que receberam, sem tentar hackear singletons do sistema).

Você está com um instinto excelente! Eu analisei as classes críticas do fluxo de Checkout e Carrinho e, de fato, encontrei um anti-pattern de injeção direta muito semelhante ao que vimos no `SessionMapper`, ocorrendo exatamente onde o dinheiro e o frete são calculados.

Ao olhar para o `TotalMapper.php`, `PaymentMapper.php` e `ShippingMapper.php`, identifiquei que dentro do loop eles estavam invocando a conexão global de banco de dados diretamente para pescar o Registry através de uma chamada estática.

**Por que isso é um problema?**
Esses três Mappers já estendem a classe `BaseMapper`, que já possui a injeção do `$this->registry`. Ao ignorar o `$this->registry` e buscar o Registry invocando estaticamente o Banco de Dados, essas classes criam um acoplamento forte. 

A solução consiste em substituir o `ConnectionDB::getRegistry()` pelas instâncias `$this->registry`.
