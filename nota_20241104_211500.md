# Refatoração: Extinção de Registro Legado em Mappers e Repositórios

**Implementação**: 
Três arquivos centrais da camada de banco de dados e orquestração de domínio foram refatorados para substituir de vez a classe `Alpha\Support\Registry`:
1. Em `ShippingMapper.php`, o construtor passou a exigir e injetar `Psr\Container\ContainerInterface`, repassando a injeção para a classe pai `BaseMapper`. Foram também alterados os comandos de consulta `.registry->get` e `.registry->has` por equivalentes no container.
2. Em `StockStatusMapper.php`, foi trocado a referência estrita do `.registry` por `.container` na consulta das configurações de sistema (captura do `language_id`).
3. Em `StoreRepository.php`, foi removido o import de `Alpha\Support\Registry`. O método de fábrica `createStoreInstance()` (usado para alimentar falsamente instâncias legadas, como o editor de pedidos) foi refatorado para tipar explicitamente instanciar a classe estrita original `\Opencart\System\Engine\Registry`.

**Motivo**: 
Essas classes representavam as últimas resistências conhecidas da dependência direta de uma estrutura obsoleta baseada em OpenCart DI. Sem essa correção, as lógicas de frete dinâmicas ou simulações de loja teriam erro fatal por falharem em instanciar a classe substituída.

**Benefício**: 
Total conformidade com o ecossistema PSR-11. As classes orquestradoras (Mappers) ganham interoperabilidade completa com testes unitários, e os repositórios protegem os limiares de dívida técnica quando precisam interagir com subsistemas de retrocompatibilidade do painel administrativo.

## Resposta Completa do Assistente
Excelente escolha! Avançamos agora para a camada de Mappers e Repositórios de Domínio da nossa aplicação, que é um lugar crítico.

Analisando o código das três classes, tomei decisões arquiteturais importantes para cada uma, respeitando suas responsabilidades. Eis o que foi feito:

1. **`StoreRepository.php`**: Diferente de uma simples injeção de dependência, este repositório utiliza um método de "Fábrica" (`createStoreInstance`) para criar um ambiente *dummy* (falso) para que o editor de pedidos legado do OpenCart funcione. Em vez de injetar o `ContainerInterface`, removi o import obsoleto do `Alpha\Support\Registry` e instanciei diretamente o `\Opencart\System\Engine\Registry` nativo. Assim isolamos a dívida técnica sem quebrar o ecossistema legado.
2. **`StockStatusMapper.php`**: Substituí o uso interno da propriedade `$this->registry->get` pela `$this->container->get`, confiando que a classe pai (`BaseMapper`) agora injeta o contêiner PSR-11 padrão do sistema.
3. **`ShippingMapper.php`**: Refatoração pesada aplicada. Removi a dependência do `Registry` no construtor e apliquei o padrão PSR-11 `ContainerInterface`, mudando também todas as chamadas internas de validação (como o `.registry->has`) e requisição de módulos.
